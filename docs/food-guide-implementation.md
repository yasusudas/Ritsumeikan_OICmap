## スマホでの拡大の軽量化（2026-10-15）

スマホで拡大すると重く、実用にならないという報告を受けて直した。iOS シミュレーター（iPhone 17、Safari）の1Fで、同じピンチ拡大・縮小・パンを行い、25msを超えたコマを数えた。

| 状態 | 25ms超のコマ | 最も遅いコマ |
| --- | --- | --- |
| 修正前 | 29 | 337ms |
| 修正前、食事ピンを隠す | 20 | 163ms |
| 修正前、食事ピンと店舗領域を隠す | 16 | 175ms |
| 修正後（2回測定） | 9 / 7 | 83ms / 103ms |

- 主因は地図本体。拡大の1コマごとに地図の幅・高さを変えるため、WebKit が階のSVG全体を描き直していた。タッチ画面（`pointer: coarse`）では、拡大中は前回描いた地図を `scale()` で伸縮し、倍率が0.14秒止まったら実寸で描き直す（`src/main.js` の `flushViewRender`）。ピンチ中の地図はわずかにぼやけ、指を止めると鮮明に戻る。Safari（WebKit。`GestureEvent` の有無で判定）もこの方式にする。Chrome などPCのブラウザーは従来どおり毎コマ描き直す。修正後に残る遅いコマは、主に指を離した後の1回の描き直し。
- Mac（M2 Pro）で同じ大きさのウィンドウを使い、ホイール入力を1コマに1回送って測った（各2回）。
  - Safari 27 は毎コマ描き直す動きで、拡大中15fps、最悪262〜301msだった。食事ピンを隠しても変わらなかった。伸縮してから描き直す動きでは60fps、最悪18〜25msだった。
  - Chrome 155 はどちらの動きでも120fps、遅いコマ0だった。
  - Safari にも適用した後、Safari 27 で `GestureEvent` があることを確かめた。拡大中は60fps、遅いコマ0、最悪23ms（2回）。止まった後に実寸で描き直されることも確かめた。
- 食事ピンは毎コマ、CSS の `drop-shadow` 2段と 1254px 四方の PNG 縮小を描き直していた。影は同じ値で描いた画像 `public/food-marks/pin-shadow.png` に置き換え、PNG は 256px 四方に縮小した（8枚で約6.4MB→約420KB。元画像は git 履歴 `148d3c5`）。
- ピンは `transform` だけで動かし、それぞれ独立した層にした。パンでは大きさ・当たり判定を書き直さない。毎コマ呼ばれる `render()` は変わった値だけを書き込み、画面の寸法を測る `insets` は使うときだけ計算する。
- 修正前に食事ピンの影を CSS で描いていた見た目とは、40pxで同じ。拡大して大きくなったピンでは影も比例して大きくなる。
- 店舗領域・施設領域の層（`.facility-area-layer`）を地図とは別の層にした（`will-change: transform`）。選択・ホバー・一覧で輪郭や塗りが変わっても、下の階のSVGを描き直さない。拡大した状態でピンが隠れる店舗カードを初めて開く手順では、最も遅いコマが57msから44msになった（シミュレーター、各1回）。
- カードを初めて開くと、約40msのコマが3つ続く（2回目以降は約25〜35ms）。日本語フォントの追加読込（カードを開いても新しいフォントファイルは取得しない）、開くアニメーション（止めても同じ）、ピンを見せるための地図の移動（移動がなくても同じ）のいずれでもなく、カードの初回描画と見られる。地図の移動を0.28秒で滑らせる案も試したが、遅いコマが増えたため採用しなかった。
- テスト87件、英語同期、検索データ検査（551件）、build 成功。PCブラウザーでピンのホバー・クリック、シミュレーターでピンのタップでカードが開くことを確認した。実機での確認は未実施。

- 緑の店舗領域の内側全体からクリック・タップでカードを開く。PCではピン外の領域内でも200ms後に概要を表示する。通常時に輪郭が非表示でも同じ範囲を対象とする。
