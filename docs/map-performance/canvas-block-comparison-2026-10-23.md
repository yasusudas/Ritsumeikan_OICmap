# 元SVGとCanvas＋ブロック読み込みの比較

## 結果

**Safariの1Fは約49 → 58〜59 FPSへ改善した。5FとFirefoxでは一貫した改善がない。消費電力の低下は未確認。** ここでいうFPSは親ページのrequestAnimationFrame（rAF）間隔による操作更新の指標であり、画面へ提示されたGPUフレーム数ではない。

改善なしDevから、元SVGをPNGブロックへ事前変換し、表示範囲のブロックをCanvas 2Dへ描く比較版を作った。前のSVGO・mask/filter置換・Leaflet・頻度変更・停止判定修正・最大ズーム変更・SVG要素の非表示は組み合わせていない。通常アプリへの採用はしていない。

実Safariと実Firefoxで計64試行を完了した。Chromeは新しいiframe文書の読み込み確認がタイムアウトし、正式な全条件比較を完了できなかった。Chromeの途中結果は以下の集計へ含めない。

画面にかかるブロックだけを要求する。表示外の既存SVG要素を一つずつ判定する前回の方式とは異なる。現在フロアのz0概要ブロックはキャッシュから追い出さず、代用描画に残す。停止中の継続描画ループは設けていない。

mask/filterを含む元SVGの表現はPNGへ焼き込む。生成器はsharp/librsvgであり、Safariが直接SVGを描く場合とラスタライズ結果は一致するとは限らない。地図以外のUIやアイコンには既存SVGが残るため、アプリ全体をSVGなしにした試験ではない。

## ブロック待ち・メモリ・通信

Canvasの計7680ズーム／パンサンプル中、976サンプル（12.7%）では粗い親ブロックを代用した。サンプル中に代用が一つでもある場合を1件と数える。**代用もできないblankスロットは0件**。これはJS側の描画状態の観測であり、全GPUフレームの白画面検査ではない。

詳細ブロックへの切替時には一時的に解像度が変わり得る。高いFPSだけで画質が一定とは判断しない。各試行の停止中60 rAFではCanvasの追加描画はすべて0回だった。

保持したデコード済み画像は最大64枚。514×514×4 bytesとして計67,634,176 bytes（64.5 MiB）、表示Canvasは900×440×4＝1,584,000 bytes（1.51 MiB）。これはアダプターが参照する画像のRGBA換算値とCanvas一面の値であり、ブラウザ全体・GPU・圧縮PNG・内部コピー等を含む実メモリ測定ではない。SVGとのメモリ優劣は未判定。

事前生成1008ブロックと追加の事前操作でサーバー側PNGキャッシュを温めてから本測定した。本測定中はサーバー生成0件・生成エラー0件・キャッシュヒット4594件。[本測定直後のサーバー記録](../../output/canvas-block-2026-10-23/paired-server-stats.json)

その後の画質・検索確認でも資産が追加され、最終ローカルキャッシュは1240 PNG、11,927,809 bytesだった。これは全試験で作ったローカル資産の合計で、初回の必要転送量でも本番配信の容量でもない。

Resource TimingのencodedBodySizeはSafariで0を返す元SVGがあり、Firefoxには重複取得もあったため、集計CSVのbytes値を実通信量の比較には使わない。今回はlocalhost・温まった生成済みPNGによる試験で、ネットワーク制限下の初回表示、CDN、オフライン、全フロアの事前生成費用は未検証。

## 消費電力について

**今回、「SVGは非常に電力を使う」「Canvasなら省電力になる」は実測で確認できていない。** powermetricsのCPU/GPU電力計測はsuperuserが必要で、sudo非対話実行もパスワード要求で使えなかった。[実行記録](../../output/canvas-block-2026-10-23/power-probe.txt)

W・J・バッテリー減少量を取得していないため、FPSやCanvasのJS描画時間から省電力率へ換算しない。ブロック化は画面外の描画を減らす一方で、PNG生成・転送・デコード・保持・合成という費用も加わる。省電力を採用根拠にするには、同じ実時間・同じ操作量・画質・画面輝度などをそろえた別の電力計測が必要。

## 不採用データ・途中修正

- 初期smokeではキャッシュ退避により代用もできないブロックがあった。z0概要ブロックを保持する修正後に正式測定を実行した。正式集計には修正前smokeを入れない。
- 3ブラウザの試行はChrome非表示や文書更新の停止で中断した。独立ウィンドウ、固有URL、iframe再生成でも、新iframeのsrcと実際の子文書URLが一致しないまま30秒の準備確認がタイムアウトする場合があり、Chromeの完了データは得られなかった。原因は特定していない。
- Chrome単独の再試行も未完了。Chromeのsmoke・途中4試行、他ブラウザの中断データは参考証跡として残すが、正式64試行には混ぜない。
- 正式測定後、Chromeの再試行向けにハーネスへ固有URL・iframe再生成、画質・検索確認を追加した。サーバーも過去Leafletキャッシュの記録がない環境で生成できるようにした。正式測定時のハーネス／サーバー／アダプターを`paired-*`として別途保存している。描画アダプターは正式測定と同じ。
