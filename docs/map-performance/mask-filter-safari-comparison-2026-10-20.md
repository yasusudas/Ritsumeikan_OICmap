# 1Fのmask/filter置き換えと実Safariでの比較（2026-10-20）

## 結果

1Fの「音楽練習室 / Music Practice Room」の薄い角丸背景に使われているmask/filterを、同じ濃度のopacityへ置き換えた。実Safariで元SVGも測り直した結果、拡大縮小のFPS中央値は日本語32.11→58.37、英語31.63→58.35へ改善した。25msを超えるフレームも約18.6%から1%未満へ減った。

見た目は目視で区別できる変化を発見しなかった。ただし完全一致ではなく、元のマスク対象背景だけに最大RGB 3/255の画素差がある。教室領域の10倍切り出しは完全一致した。

Version 3.1以降に向けた `refactor/map-scale` の検証。候補SVGを別ファイルで作成し、元SVG・通常ビルド・本体の拡大縮小処理は変更していない。前回のSVGO版も今回の比較には使っていない。

## 何を置き換えたか

日英1Fには、それぞれfilter定義1個、mask定義1個、そのmaskを参照するg要素1個がある。

- filterの `feColorMatrix` はRGBを白にして、alphaは元のままにする行列。
- mask内の塗りはSVG全体より広い一定濃度の領域。日本語は `fill-opacity=".1"`、英語は `fill-opacity="0.100006"`。
- 対象はB棟の音楽練習室ラベルの背景で、複雑なシルエットを切り抜いているわけではない。

白の輝度マスクは、そのalphaを対象の透明度に掛ける処理になる。この既知の一定濃度マスクを、対象gのopacityに置き換えた。一般のマスクを無条件に置き換えるものではない。([W3Cのマスク処理モデル](https://www.w3.org/TR/css-masking-1/#MaskValues)、[feColorMatrixの仕様](https://www.w3.org/TR/filter-effects-1/#feColorMatrixElement))

```xml
<!-- 日本語版の参照部分。定義側のfilter/maskも削除する -->
<g mask="url(#Fl)">…</g>
<!-- 置き換え後 -->
<g opacity=".1">…</g>
```

英語も同様に `mask="url(#mask-0)"` を `opacity="0.100006"` に置き換える。

パス・色・座標・文字・viewBox・clip-pathは維持した。SVGO、数値の丸め、タイル化、最大倍率の変更は行っていない。原本日英2画像と、旧食事ピクトグラム除去後の閲覧用日英2画像を別途生成した。

XMLの構造を比較し、filter/mask定義の削除と上の属性変更以外は一致することを4画像で確認した。比較ではXMLの整形用空白だけを無視した。候補画像内のmask/filter定義・参照はすべて0。

## 比較条件

- 基準コミット: `cb403e0a0c882b0de79ae0182a3a98988f9097e4`。
- macOS 27.0.1、実アプリのSafari 27.0.1。WebKitのエミュレーターやiPhoneシミュレーターではない。
- アプリと地図の表示領域960×800 CSS px、DPR 1。前回のSVGO検証と同じ。
- 今回の親ページは全16試行で1025×1094。前回の親ページは1025×1132で、ブラウザのタブバー等の領域が異なるが、比較対象iframeと地図は前回・今回とも960×800で完全に表示されている。
- 前回と同じproduction buildを使い、元版を `/baseline/`、置き換え版を `/no-effects/` で提供。違いは対象SVGだけ。JS・CSS・JSON・食事ピンは同じ。
- 共通JS: `main-D_OuRnt9.js`、SHA-256 `f4eaa731801ce9abc01efc0866fe0c16b0cbc16676fff4531e8b391ca36d4859`。
- 本体は従来どおり、Safariではscaleを使いながら倍率が変わる4フレームに1回描き直す。停止後140msの描き直しも同じ。
- localhost専用Service Workerはキャッシュ処理なし。前回同様 `Cache-Control: no-store` を付け、別の実験の資産が混ざらないようにした。

## FPSの計測方法

日英の1Fを各条件4回、計16試行。順序は元→置換→置換→元→置換→元→元→置換。前回の計測ページを設定で切り替え、`load`、`warm`、`wheel`、`measure`、`stats` の関数本体と待ち時間は変更していない。

各試行でページを読み直し、24段階の拡大・縮小でウォームアップする。その後、同じ合成ホイール操作で24段階の拡大と24段階の縮小を3往復。倍率の変化は本体どおり1段階1.1倍で、上限に達して停止する時間は作らない。停止後の18フレームと、拡大後のドラッグ60フレームは別枠で記録した。

FPSは親ページのrequestAnimationFrame間隔から算出した操作更新の指標であり、GPUの表示フレーム数を直接数えたものではない。実トラックパッドのピンチ操作の値でもない。前後を同じ方法で比較している。

採用した拡大縮小サンプルは144×16=2,304フレーム。非表示状態のフレームは全試行0、全試行のviewportとDPRも一致した。外れ値を除外していない。

## FPSの結果

FPSとp95は各4試行の中央値。「25ms超」は4試行の全576フレームに対する割合。

| 対象 | 条件 | FPS中央値 | FPS範囲 | p95フレーム時間 | 25ms超 | 最大フレーム時間 |
|---|---|---:|---:|---:|---:|---:|
| 日本語1F | 元SVG | 32.11 | 31.58–32.80 | 127.0ms | 18.58% | 277ms |
| 日本語1F | mask/filterなし | 58.37 | 57.83–60.25 | 21.0ms | 0.52% | 32ms |
| 英語1F | 元SVG | 31.63 | 31.50–31.81 | 130.0ms | 18.58% | 275ms |
| 英語1F | mask/filterなし | 58.35 | 57.81–59.65 | 22.5ms | 0.69% | 44ms |

FPS中央値の改善は日本語+81.76%、英語+84.45%。どちらの言語でも、置き換え版4試行すべてが元版4試行すべてを上回った。FPSだけでなく、長いフレームの頻度も減っている。

停止後の区間の最大フレームは、日本語で元30ms→置換29ms、英語で元31ms→置換34ms。停止後もあらゆる指標が改善したとまでは言わない。生フレーム列とパンの結果も保存している。

今回の条件では、このmask/filterを一定opacityへ置き換える方法は有力な改善候補と判断できる。maskとfilterを同時に置き換えているため、どちら単独がどれだけ寄与したかは分離していない。

## 見た目の結果

実Safariのcanvasへ元画像・候補画像を同じ大きさと白背景で描いて比較した。原本と閲覧用の日英4画像について、以下4条件、計16条件を確認した。

1. SVG全体を1倍で描画（1191×842px）。
2. SVG全体を4倍で描画（4762×3368px）。
3. 前回と同じ、横70%・縦45%を中心とする10倍の教室領域（1600×1100px）。
4. 今回の変更対象である音楽練習室の背景付近、SVG座標(458.2, 679.5)を中心とする10倍の切り出し（1000×500px）。

原本と閲覧用の画素差は一致していたため、下表は言語別にまとめる。

| 対象 | 条件 | 変わった画素数 | RGB各成分の差の最大値 | 差が8/255を超える画素 |
|---|---|---:|---:|---:|
| 日本語 | 全体1倍 | 300 / 1,002,822 | 1 / 255 | 0 |
| 日本語 | 全体4倍 | 4,818 / 16,038,416 | 1 / 255 | 0 |
| 日本語 | 教室領域10倍 | 0 / 1,760,000 | 0 | 0 |
| 日本語 | マスク対象10倍 | 29,975 / 500,000 | 1 / 255 | 0 |
| 英語 | 全体1倍 | 523 / 1,002,822 | 3 / 255 | 0 |
| 英語 | 全体4倍 | 8,420 / 16,038,416 | 1 / 255 | 0 |
| 英語 | 教室領域10倍 | 0 / 1,760,000 | 0 | 0 |
| 英語 | マスク対象10倍 | 52,116 / 500,000 | 1 / 255 | 0 |

1倍での差は日本語でx=439〜478・y=675〜683、英語でx=424〜492・y=675〜683の範囲に限られた。元のマスク背景の位置と一致する。全体画像と対象ラベルの拡大比較を目視し、色・文字・輪郭に見分けられる変化は発見しなかった。

完全一致とは扱わない。一定濃度マスクとopacityでの透明度合成・丸めの違いによる可能性があるが、Safari内部の原因は直接調べていない。また、このcanvas比較はSVGが対象であり、HTMLの食事ピンやカードまで画素比較したものではない。実アプリの表示・拡大縮小・ドラッグと食事ピンの表示もSafari上で確認した。error/unhandledrejectionイベントは0だったが、開発者コンソールの全ログは未取得。

## 容量

今回の主な効果は描画性能で、容量の削減は小さい。

| 表示用画像 | 元 | 置換後 | 削減 |
|---|---:|---:|---:|
| 日本語1F（食事ピクトグラム除去後） | 338,937bytes | 338,629bytes | 308bytes |
| 英語1F（同上） | 1,023,929bytes | 1,023,558bytes | 371bytes |

前回のSVGOは英語1Fを53.41%小さくしたが、FPSはほぼ変わらなかった。今回の結果と合わせると、少なくともこの1F・Safari・表示条件では、ファイルサイズだけでは操作中の負荷を説明できない。

## 再実行

通常ビルドを作り、以下の比較サーバーを起動する。SVGOや新しい依存関係の導入は不要。

```sh
node node_modules/vite/bin/vite.js build --manifest --outDir /tmp/oic-svgo-build
node scripts/benchmarks/mask-filter-safari-server.mjs \
  /tmp/oic-svgo-build output/mask-filter-safari-2026-10-20 5192
```

実Safariで `http://127.0.0.1:5192/` を開き、「見た目の画素比較」→「FPS比較」を実行する。FPS計測中はSafariを前面に保ち、960×800のiframeをウィンドウ内に完全に表示する。`?run=visual` / `?run=perf` でも開始できる。

```sh
python3 scripts/benchmarks/summarize-mask-filter-safari.py \
  output/mask-filter-safari-2026-10-20
```

Pillowがあれば比較PNGも生成する。変換処理は `scripts/benchmarks/first-floor-without-mask-filter.mjs` に分離し、既知の行列・マスク範囲・参照数と異なるSVGでは停止する。
