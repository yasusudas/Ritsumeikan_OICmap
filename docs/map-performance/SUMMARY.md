# 地図の拡大縮小・描画性能：検証結果まとめ

## 全体の判断

**1Fの滑らかさと見た目を両立する候補として、今回の結果ではmask/filter置換が有力。** scaleのみ・描き直し頻度の削減でもFPSは上がるが、拡大中の鮮明さとの交換になる。Leafletは約60 FPSを出せた一方、再測定では低下とタイル待ちが増えており、安定性と移行コストが残る。

SVGOは容量削減に効果があるが、ズームFPSの改善は確認できなかった。最大ズーム制限、最終入力140msへの停止判定修正、SVGの画面外非表示も、それぞれ単独では今回の1F負荷を解消しなかった。**異なる試験間のFPSだけで方式の順位や、組み合わせた場合の効果を決めない。**

10月23日のCanvas＋ブロック読み込みでは、別の画面寸法・入力列でSafari 1Fの改善を確認した。Firefoxには一貫した改善がなく、PNGの画質差・代用ブロック待ちも残る。**省電力は未確認で、SVG全般が不適切とは結論しない。**

## 読み方・共通条件

2026年10月20〜21日の測定を10月22日に整理し、10月23日にCanvas検証を追記したもの。基準は改善なしDev `cb403e0a0c882b0de79ae0182a3a98988f9097e4`。各候補はこの基準から独立して作り、前の改善を積み重ねていない。現行mainを測り直した結果ではない。

実Mac版Safari 27.0.1、地図領域960×800 CSS px、DPR 1が基本。FPSはrequestAnimationFrame間隔による操作更新の指標で、GPUが提示した実フレーム数ではない。通常は各条件4試行の中央値。入力経路・停止区間・親画面寸法などには試験間の違いがあり、以下は各試験内の比較として読む。画質はSVGをSafariのcanvasへ描いた比較と、実Safariウィンドウの撮影を使い分けている。

第11節だけは直前のブラウザ比較に合わせた900×440・120段階で、実SafariとFirefoxを同期して測定した。第1〜10節の絶対FPSとは直接比較しない。

## 1. SVGOによるSVG軽量化

| 1F | Dev FPS → SVGO FPS | SVG容量の削減率 |
|---|---:|---:|
| 日本語 | 32.03 → 31.64 | 0.81% |
| 英語 | 31.58 → 32.04 | 53.41% |

英語SVGの容量は大きく減るが、FPSはほぼ変わらない。確認範囲に文字・部屋・記号の欠落はなく、輪郭等の画素差はある。通信量削減の候補であり、初回ロード時間の実測やズーム高速化を証明したものではない。[詳細](svgo-safari-comparison-2026-10-20.md)

## 2. 1Fのmask/filterをopacityへ置換

| 1F | Dev FPS → 候補FPS | 25msを超えるフレーム |
|---|---:|---:|
| 日本語 | 32.11 → 58.37 | 18.58% → 0.52% |
| 英語 | 31.63 → 58.35 | 18.58% → 0.69% |

音楽練習室の薄い角丸背景に使う一定濃度のmask/filterを、同じ濃度のopacityへ置換した。容量減は308／371bytesだけで、SVGOの容量削減とは別の効果。目視で変化を見つけず、教室領域10倍は画素一致。背景付近等には最大RGB 3/255の微差がある。

**見た目への影響を小さく保ってFPSが改善した有力候補。** 一般のmaskをすべてopacityにできるわけではなく、maskとfilterそれぞれ単独の寄与も未分離。[詳細](mask-filter-safari-comparison-2026-10-20.md)

## 3. Leafletタイル化：描画のみ

| 1F | Dev FPS → 候補FPS |
|---|---:|
| 日本語 | 32.43 → 59.04 |
| 英語 | 30.44 → 59.41 |

元SVGをPNGタイルへ変換し、操作はDevのままLeafletで描画した。5Fは元から約60 FPSで、改善は小さい。余白付きタイルと通常合成で、実画面に出た明るい境界線を修正した。

PNG化による文字・細線の輪郭差は残り、停止してもSVG画質へ戻らない。ズーム中に読み込み済みタイルDOMが0枚のサンプルもあり、表示待ちを確認した。これはGPUの白画面枚数の直接測定ではない。JS/CSS・PNG資産が増え、生成・配信・更新方法も必要。**高速化の可能性はあるが、FPSだけで採用できない。** [詳細](leaflet-tiles-safari-comparison-2026-10-21.md)

## 4. Leaflet：操作も全面移行

wheel・ドラッグ・ピンチ等をLeaflet標準ハンドラへ、検索移動をflyToへ移した検証版。検索・施設・店舗の既存DOMは追従させる。エディター移行や全ピンのL.Marker化は含めない。

同じ24段階・約9.85倍の倍率経路での比較：

| 測定 | 日本語1F：Dev → 全面版FPS | 英語1F：Dev → 全面版FPS |
|---|---:|---:|
| A：検索修正前・各4回 | 35.71 → 59.95 | 42.71 → 59.98 |
| B：検索修正後、全フロア等の確認後・各4回 | 23.67 → 41.79 | 26.64 → 24.78 |
| C：新規ウィンドウでの追試・各1回 | 32.37 → 60.05 | 未測定 |

A/B間のソース差は検索時の予約描画と飛行の順序だけで、FPS試験のwheel・描画実装は同じ。Bでは5Fのタイル版も低下し、タイル待ちが増加した。CはBから約2時間13分空いており、回復をウィンドウ再作成だけの効果とは断定できない。**安定60 FPS、または描画のみ版への上乗せ効果は未確認。**

同じwheel入力を送る別試験では、Dev約9.85倍に対し全面版は約1.78倍しか拡大しない。標準wheelの集約・感度・CSSアニメーションが異なるため、そこで約59 FPSでも同倍率の速度改善とは扱わない。

日英検索、全フロア・プリンター図、施設・店舗、言語切替を確認。検索枠は150コマで最大0.775 CSS pxの追従誤差。PNGの画素差、慣性・感度・境界制限などの操作差は残る。[詳細とA/B/C全結果](leaflet-tiles-safari-comparison-2026-10-21.md#leaflet-full)

## 5. 拡大中はwidth/heightを変えず、transformのみ

| 1F | Dev FPS → 候補FPS | 停止区間込みFPS |
|---|---:|---:|
| 日本語 | 32.63 → 57.57 | 40.66 → 58.63 |
| 英語 | 32.29 → 57.95 | 40.32 → 58.75 |

途中の実寸更新をなくし、停止140ms後に描き直す。5Fは約60 FPSのまま。**拡大中は文字・細線が明確にぼやけ、停止後に鮮明さが戻る。** 比較した領域では停止後の地図内容の画素も戻った。

今回の実Macでは停止区間込みでも改善した。以前のiPhoneシミュレーターとは端末・入力・指標が異なるため、「transformなら常に速い」「再描画を減らすほど速い」とは一般化しない。[詳細](scale-only-safari-comparison-2026-10-21.md)

## 6. 描き直し頻度を1/2・1/3・1/4・1/5へ変更

| 頻度 | 日本語1F FPS | 英語1F FPS | 今回の操作中の最大CSS引き伸ばし率 |
|---|---:|---:|---:|
| 元Dev（1/4） | 32.51 | 32.22 | 1.331倍 |
| 1/2 | 37.78 | 37.51 | 1.1倍 |
| 1/3 | 42.50 | 42.14 | 1.21倍 |
| 1/4の独立対照 | 32.61 | 30.89 | 1.331倍 |
| 1/5 | 50.55 | 50.53 | 1.4641倍 |

この固定入力では1/5が最も高く、停止区間込みでも約54.2 FPS。ただしDevよりぼやけるコマがあり、1/2・1/3は今回の引き伸ばしが小さい。停止後の比較では地図内部の画素が一致した。表の倍率はこの入力での観測値であり、任意のピンチに対する一般上限ではない。[頻度比較の詳細](scale-only-safari-comparison-2026-10-21.md)

## 7. なぜ1/4だけ低かったか

低下は特定の縮小範囲へ集中し、SVG表示の待ち・実寸更新の位相・140ms停止タイマーが重なっていた。次の入力をrAF完了まで待つ測定なので、描画の待ちが入力の空白になり、停止更新も割り込む。

- 操作中の停止更新を診断時だけ抑制：32 FPS前後 → 約35.6 FPS。
- 1/4のまま更新位相を2コマ変更：約49.4 FPS。
- 旧ピンチの接点距離変化を実Safariへ送る：1/4が60.03 FPSとなり、1/2・1/3を上回る。

**1/4が常に遅いという結論ではない。** 旧iPhoneシミュレーターの1/4最速という結果とは、入力・倍率経路・集計方法を分けて読む。WebKit内部のGPU・画像バッファ等の待ちの内訳は未分離。[追加調査](scale-only-safari-comparison-2026-10-21.md)

## 8. 1/4のまま、停止判定を「最後の入力から140ms」へ修正

日本語1Fは32.40 → 32.40 FPS、英語1Fは32.10 → 32.15 FPSで、主FPSの改善はない。一方、50ms指定間隔の入力診断では、最終入力から140ms未満の早すぎる停止更新が10回 → 0回になった。候補のタイマー更新19回はすべて140〜142ms後だった。

停止後は比較した6場面の内部画素が一致し、2場面だけ右端2pxに微差。**停止期限の正しさは改善したが、SVG表示の重さ自体を解消する修正ではない。** [追加検証](scale-only-safari-comparison-2026-10-21.md)

## 9. 最大ズーム上限を10から6・4・2へ変更

同じ倍率範囲では約40〜41 FPSで、一貫した改善はない。各上限までの受理入力では、日本語1FはDev39.89 → 上限6で44.34、4で42.41、2で40.80 FPS。上限で動かなくなった入力を混ぜた高いFPSを、高速化とは扱わない。

上限6は既定の検索zoom6を保つが、手動の最大拡大は現状の60%になる。上限4・2では検索後の部屋の縦横もDevの2/3・1/3へ縮む。同倍率の停止後画素は一致。**読みやすさ・拡大余地を減らす変更で、同倍率の描画負荷の解決策ではない。** [詳細](max-zoom-safari-comparison-2026-10-21.md)

## 10. 既存SVGで画面外の要素だけ非表示

| 1F | Dev FPS | インライン全表示FPS | 画面外非表示FPS |
|---|---:|---:|---:|
| 日本語 | 32.64 | 38.44 | 38.19 |
| 英語 | 32.36 | 38.05 | 37.60 |

約84〜91%の判定単位を非表示にしても、全表示対照からの上乗せはなかった。Devとの差を画面外非表示の効果と解釈しない。

さらに日本語5Fの矢印線2本が欠落し、停止後も戻らなかった。SafariのSVG useがgetBBoxでゼロ矩形を返すため誤判定した。**この試作は不採用。** 画面外非表示という方式全体の否定ではなく、今回の実装で改善と視覚同等性を得られなかった結果。[詳細](svg-viewport-safari-comparison-2026-10-21.md)

## 11. Canvasと表示範囲のブロック読み込み

元SVGをPNGブロックへ事前変換し、表示範囲だけをCanvas 2Dへ描く。操作・検索・施設DOMはDevのまま。Leafletや過去の改善は加えていない。実Safari・Firefoxで日英1F／5F各方式4回、計64試行を完了した。

| Safari | Dev → CanvasのズームFPS |
|---|---:|
| 日本語1F | 48.89 → 58.30 |
| 英語1F | 48.11 → 58.96 |
| 日本語5F | 57.71 → 57.83 |
| 英語5F | 58.76 → 58.80 |

1Fの25ms超率は日本語15.00%・英語15.83%から、ともに0.83%へ減少。Firefoxの親rAFは約111〜116 FPSで一貫した改善がなく、CSS変化は約57〜65回／秒だった。親rAF値を画面の提示FPSとは扱わない。

Canvasの7680操作サンプル中976件では粗い親ブロックを代用し、代用もできないblankは0件。保持画像のRGBA換算は最大64.5 MiB＋表示Canvas1.51 MiBで、ブラウザ全体の実メモリ測定ではない。温まったlocalhost資産での比較のため、本番通信や初回生成の負荷は未確認。

日英1F／5Fの実Safari画像16枚とFirefox日本語1Fの4枚を保存。Safariの撮影位置では拡大中のぼやけが小さい一方、停止後もSVGとは輪郭差が残る。確認した検索枠・トイレ表示の座標は一致した。**CanvasはSafari 1Fの改善候補だが、省電力や全ブラウザでの優位は未証明。** Chromeは新iframe文書の準備確認がタイムアウトし、正式比較は未完了。[詳細・比較画像・全結果](canvas-block-comparison-2026-10-23.md)

## 次の判断に使うポイント

| 目的 | 今回の結果からの候補・判断 |
|---|---|
| 1Fの画質を保ちつつ滑らかにする | 特定mask/filterの置換を優先して検討。実端末・他条件での確認は必要 |
| SVGの転送量を減らす | SVGO。FPS向上とは分けて評価 |
| 拡大中のぼやけを許容して速度を上げる | scaleのみ、または頻度調整。入力条件ごとの再確認が必要 |
| 地図操作の基盤をLeafletへまとめる | 操作移行は試作できたが、再測定の低下・PNG画質・待ち・感度・配信設計が残る |
| 地図描画をCanvasとブロックへ移す | Safari 1Fの改善候補。PNG画質・粗いブロックの代用・資産配信・Chrome正式比較が残り、省電力は未確認 |
| 現状のまま採用を見送るもの | 今回の画面外非表示試作。最大ズーム制限は性能より使い勝手の判断 |

各試験の終了時点では、候補の通常アプリへの採用・commit/push/deployは行っていない。複数改善の組み合わせ効果、物理iPhone・実トラックパッド、本番通信・冷えた起動、長時間使用時の安定性は未確認または十分な切り分けがない。プリンター図単独の軽量化は独立計測しておらず、通常の1F改善とは切り分ける。
