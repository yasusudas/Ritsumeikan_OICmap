# SVGの表示範囲外を非表示にする試作と改善なしDevの実Safari比較（2026-10-21）

## 結果

**この試作では、画面外を非表示にすることによるFPSの上乗せは確認できず、日本語5Fでは画面内の矢印の線が欠落した。現状の候補は採用しない。**

実Safariで48試行を測り直した。1Fの拡大縮小FPS中央値は、日本語がDev32.64→全表示38.44→画面外非表示38.19、英語が32.36→38.05→37.60だった。Devからの差は主に縮小区間に出ており、インライン全表示でも同程度の結果になる。画面外非表示だけの効果として扱えない。5Fとパンは多くの試行で約60 FPSだった。

見た目は全面的な同等性を満たさない。日本語5FでSafariの`getBBox()`が長さのある線の`use`にもゼロ矩形を返し、画面内の線を画面外と誤判定した。停止しても復元しない。検索、フロア往復、施設・店舗操作が通ることとは別の不具合である。性能測定後に候補を修正・差し替えず、以下はすべてこの同じ候補の結果として残す。

## 比較する実装

基準はfetchで確認した`origin/dev`の`cb403e0a0c882b0de79ae0182a3a98988f9097e4`。`refactor/map-scale`の通常ソースを変更せず、Viteのビルド時変換だけで候補を作った。SVGO、mask/filter置換、Leaflet、最大ズーム変更、scale-only、描き直し頻度変更、停止タイマー修正は重ねていない。

現在のDevはSVGを1枚の外部`img`として表示する。そのままでは内部の部屋・文字をJavaScriptで個別に非表示にできないため、候補では原本SVGをインライン化した。インライン化自体の影響を分けるため、次の3条件を比較する。

### 非表示の単位と範囲

文字の一部だけ欠けることを避けるため、SVGルート直下の描画要素・グループを単位にする。初回マウント時に`getBBox()`とCTMから原本座標系の矩形を一度計算し、8 SVG単位の余白を加えて保持する。元の描画flush時に地図の位置・論理サイズとviewerから表示矩形を逆算し、64 CSS pxの画面外余白を含めて交差判定する。毎フレームの`getBBox()`や`getComputedStyle()`は行わず、表示状態が変わった単位だけstyleを書き換える。

defsは常に残し、mask/filterを持つ、または配下に持つ描画グループも安全側で常時表示する。したがって厳密に「画面内だけ」ではなく、**余白と効果を持つグループを残した保守的な非表示処理**である。SVG全体を取得・解析し、非表示ノードもDOMに保持する。通信量やDOM数を減らす試作ではない。フロアごとのDOM・境界矩形をキャッシュするため、そのメモリは残る。メモリ使用量自体は今回測定しない。

Shadow DOMはSVG内のstyleとIDをアプリや検索・施設のSVGから隔離するために使う。透明なサイズ保持用imgを元の位置へ置き、インラインSVGを同じ`.map-asset`内へ重ねる。検索・施設・フードピンのレイヤーは元の実装を使う。フードレイヤーには原本SVGのURLを渡して、言語の判定を維持する。

### 日本語5Fの矢印欠落の原因

日本語5Fの`<use href="#Ez">`4個は、実Safariで表示を戻してから測っても`getBBox()`が`{x:0,y:0,width:0,height:0}`を返した。そのうち画面内の2個は`getBoundingClientRect()`では次の値を持った。

- ルート直下index261：x92.051、y377.072、width0、height356.361 CSS px。
- index263（`x="20.598"`）：x210.354、y377.072、width0、height356.361 CSS px。

位置はiframe内の値。幅0の線でもストロークは画面内に描かれる。一方、試作はゼロ矩形を原点付近の小さな矩形として扱い、8 SVG単位の余白を付けても画面外と判定した。`getBBox()`は例外を出していないため、既存の例外時常時表示フォールバックに入らなかった。停止後の差分画像でも、この2本の線に沿った差を確認した。

[実Safariの境界診断](../../output/svg-viewport-safari-2026-10-21/diagnostic-ja-5F-bounds.json) / [欠落箇所の差分画像](../../output/svg-viewport-safari-2026-10-21/difference-ja-5F-23.png)。

修正するなら、まずゼロ・不確実な境界を常時保持するか、初回に別の境界取得へフォールバックする必要がある。今回の5件の座標計算テストは計算式を検証するが、SafariのSVG境界APIが正しい矩形を返すことまで保証しない。**フォールバック修正版のFPS・見た目は今回未測定**であり、測定済み候補と混ぜない。

```sh
node scripts/benchmarks/build-svg-viewport-candidates.mjs
node --test scripts/benchmarks/check-svg-viewport-math.mjs
node scripts/benchmarks/svg-viewport-safari-server.mjs
```

実Safariで`http://127.0.0.1:5201/?run=perf`を前面表示する。出力は既定では同じフォルダーへ上書きされるため、再測定時は既存証跡を退避するかserverの第3引数に別出力先を渡す。画質は`?run=quality&variant=svg-cull&language=ja&floor=5F&steps=23`で拡大中を保持し、Safariネイティブ撮影後に「停止後の描画」を押して再撮影する。`steps=0`で初期表示、`&pan=1`で大きなパンを追加する。`run=usage`、`run=controls`、`run=inspect`が検索・操作・境界診断。画質の保持処理はperfでは実行しない。

```sh
node scripts/benchmarks/summarize-svg-viewport-results.mjs
python3 scripts/benchmarks/compare-svg-viewport-screenshots.py
```

画像比較にはPillowとNumPyが必要。ネイティブ画像の切り出し・解析だけを行う。[測定ページ](../../scripts/benchmarks/svg-viewport-safari-page.js)と[集計スクリプト](../../scripts/benchmarks/summarize-svg-viewport-results.mjs)も保存している。
