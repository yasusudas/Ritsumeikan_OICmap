# Leafletタイル移行とバニラDevの実Safari比較（2026-10-21）

## 結果

元DevのSVGをPNGタイルへ変換し、Leafletで表示する試作を比較した。実Safariでの拡大縮小FPS中央値は、日本語1Fが**32.43→59.04（+82.08%）**、英語1Fが**30.44→59.41（+95.15%）**。5Fは元から約60 FPSで、大きな改善はない。

**画素単位では元SVGと同一ではない。** 初期試作で発生したタイル境界の細線は、余白付きPNGと通常合成で解消し、その最終設定でFPSを測り直した。一方、PNGへの変換・表示による輪郭の差と、ズーム中のタイル読み込み待ちは残る。高速化の可能性は確認できたが、本体への採用には追加検証が必要。

Version 3.1以降に向けた `refactor/map-scale` の独立した検証。アプリ本体、原本SVG、通常ビルドの設定、依存定義は変更していない。コミット・push・デプロイは行っていない。

- SVGOなし、mask/filterのopacity置換なし、最大倍率の変更なし。元Devのmask/filterをそのままタイル生成時に描画する。
- 操作側の実装もDevのまま。Safariでは途中をscaleで伸縮し、倍率が変わる4フレームに1回と停止140ms後に本来のサイズへ更新する。最大倍率10も維持。
- 全18枚の原本・閲覧用SVGは、基準ビルドと候補ビルドでSHA-256一致。終了時に通常ビルドを作り直し、計測基準のJS／CSS／SVG計67ファイルと完全一致した。

## 何を移行したか

Leaflet 1.9.4の `CRS.Simple` と `TileLayer` を使い、フロアSVG全体を伸縮する画像の代わりにPNGタイルを表示する。Leafletが画面付近のタイルと周囲のバッファを管理する。方式の参照は [LeafletのCRS.Simple例](https://leafletjs.com/examples/crs-simple/crs-simple.html) と [GridLayerのAPI](https://leafletjs.com/reference.html#gridlayer)。

- 元SVGのworld幅を1024とし、画像上端を原点にする。H棟のviewBox原点も含め、元座標を対応させる。
- CSSのタイル幅256px、PNGの中身512px、周囲1pxの余白を付けた514×514px。native zoomは0〜4、`keepBuffer: 1`、範囲外の繰り返しなし。余白を重ねるため、Leaflet標準の加算合成を`mix-blend-mode: normal`へ変更する。
- sharp 0.34.5／librsvg 2.61.2で元SVGを描画。タイル書き出し用のroot幅・高さ・viewBoxだけを変え、mask/filter・パス・文字・色・クリップを保持する。
- Devの拡大率・移動量からLeafletの中心・倍率を計算する。検索外周、施設リング、食事ピンは既存の層を重ねる。
- Viteの検証専用変換でアダプターを差し込む。元の `<img>` は透明なプレースホルダーに置き換え、SVG本体のブラウザでの再ラスタライズを避ける。

**この前半の比較はタイル描画・可視範囲管理の試作であり、操作はDevのまま。操作もLeafletへ移した追加比較は[後半](#leaflet-full)へ追記した。** 同じDevのホイール・ドラッグ入力で描画方式を比較するため、この範囲にした。SVGからPNGへ変える効果と、タイルへ分割する効果の寄与は分離していない。

## 計測条件

- macOS 27.0.1、実アプリのSafari 27.0.1。WebKitエミュレーターではない。
- iframe／地図領域960×800 CSS px、DPR 1。親ページ1025×1094、画面2048×1330。これまでの比較と同じ地図領域。
- 同じローカルサーバーのproduction build。基準 `/baseline/`、候補 `/leaflet/`。Service Workerのキャッシュ処理なし、レスポンスは `Cache-Control: no-store`。
- 日英1F／5F、各条件4回、計32試行。各ケースの順序はDev→タイル→タイル→Dev→タイル→Dev→Dev→タイル。
- 各試行で読み直し、24段階の拡大・縮小でウォームアップ。計測は24段階の拡大・縮小を3往復。1段階1.1倍で、24段階後は約9.85倍。停止後18フレームずつと、拡大後のドラッグ60フレームは別に記録。
- 各ケースの正式計測前に、タイル版で同じ操作を一度実行してタイルを事前生成。**全32試行で計測区間中の新規タイル生成は0**。PNG生成のCPU負荷がFPSへ混入することを避けた。タイルの取得・デコード・DOM更新は計測対象に含まれる。
- 採用した拡大縮小サンプルは144×32＝4,608。非表示フレーム0、viewport／DPRの不一致0、取得したerror／unhandledrejectionは0。予備計測2試行は正式結果に含めず、正式試行の外れ値は除外していない。

FPSは親ページのrequestAnimationFrame間隔から求めた**操作更新の指標**。GPUの提示フレーム数や、実トラックパッドのピンチFPSを直接測った値ではない。初回ロード・本番ネットワークの速さも、このウォーム状態の結果からは判断しない。

## 操作もLeafletへ移す全面移行の追加比較（2026-10-21）

この節は、前半の描画だけの試作から、閲覧地図の操作主体もLeafletへ移した比較である。通常のアプリソースは変更せず、`refactor/map-scale`上の検証用buildとして作成した。本番適用・採用・pushは別の判断であり、今回行っていない。

### 3条件と移行した範囲

今回もfetch後の改善なし`origin/dev`、`cb403e0a0c882b0de79ae0182a3a98988f9097e4`を基準に測り直す。前半の測定値を基準として転用しない。3buildの原本・閲覧用SVG18個はSHA-256一致。SVGO、mask/filter置換、最大ズーム変更、scale-only、描き直し頻度・停止期限の修正は重ねていない。PNGタイルが元のSVGの効果を焼き込む点と、余白・通常合成は前半と同じ。

| 条件 | 地図の描画 | 操作・カメラ |
|---|---|---|
| Dev | 元の外部SVG img | 元のwheel/mouse/touch、1/4実寸更新＋flush後140ms |
| 描画のみ | LeafletのPNGタイル | 元Devの操作・位置・アニメーションを維持 |
| 全面移行 | 同じPNGタイル | Leaflet標準の操作ハンドラ、moveイベントからUIへ座標反映 |

全面移行版では、元のwheel/mouse/touch入力リスナーを検証buildから外し、Leaflet1.9.4の`ScrollWheelZoom`、`Drag`、`TouchZoom`、`DoubleClickZoom`、`Keyboard`、`BoxZoom`を有効化した。検索などの`animateView()`はLeafletの`flyTo()`へ委譲し、元Devの1/4描き直し・停止タイマーは全面移行版の地図操作には使わない。これは移行に伴う構造の変更で、過去のscale-only候補を追加したものではない。

検索データ、検索・施設・店舗のUIと描画は既存DOMを維持する。Leafletの`move`から座標・倍率を反映し、検索枠・施設リング・店舗ピンを追従させる。全ピン・多角形を`L.Marker`/`L.Polygon`へ置き換える改修は今回含めない。ズームの標準CSSアニメーション中も追従するよう、地図に追従する3レイヤーを透明wrapperへまとめ、`zoomanim`の変換と250msのカーブを同期し、`zoomend`で確定座標へ戻す。メニューや店舗詳細カードは固定する。

- CRS.Simple、世界幅1024。Leaflet zoomは`log2(baseWidth × appZoom / 1024)`。元の初期fit・minZoom・maxZoom10を同じ範囲へ変換する。
- 上下の操作UIの安全領域を考慮してmaxBoundsを延長し、maxBoundsViscosity=1。Leafletの画素丸めと境界制限も使うため、同倍率でもDevとカメラ位置が完全一致するとは限らない。
- wheelDebounceTime=40ms、wheelPxPerZoomLevel=60、zoomSnap=0。doubleClick/keyboardのzoomDeltaは元の1.1倍刻みに合わせた`log2(1.1)`。慣性あり、zoomAnimationあり。fadeAnimation/markerZoomAnimationは無効。
- 原本SVGの変更・依存定義の変更はなし。Leafletとsharpは検証用の別依存ディレクトリーから使用した。

### 倍率をそろえる比較と、同じ入力を送る比較

実Safari27.0.1、DPR1、screen2048×1330。全条件の親viewport1024×1132、アプリ・iframe960×800、親内原点(32.5,100)。no-store、SWなし。同じローカルサーバーとproduction buildを使い、計測中にスクリーンショットや別の重い処理を入れない。

標準Leafletはwheel入力を40ms単位でまとめ、OS別のdelta正規化、非線形変換、CSSアニメーションを通す。Devはdeltaの符号だけで1.1倍へ変える。**同じ回数のwheelを送っても、同じ倍率範囲を動かす比較にはならない。** そこで各試行をfresh navigationで次の2つに分けた。

1. **同倍率（common）**：Dev・描画のみは元のwheelへ±1。全面移行版は公開APIの`setZoomAround(L.point(x,y), zoom, {animate:false})`へ同じ1.1倍刻みを送る。全条件で24段階・約9.8497倍の倍率経路を通す。全面版の描画・座標反映を同倍率で比べる試験で、Leaflet標準wheelハンドラそのもののFPSではない。境界制限・画素丸めによりカメラ位置は完全一致ではなく、元のMouseEventの整数座標と公開Pointの小数座標にも0.2 CSS pxの入力位置差がある。
2. **同入力（native）**：全条件へdeltaY±36 CSS pxの同じwheelイベントを1rAFごとに24回送る。全面移行版は標準wheelとCSSアニメーションを通す。実際の到達倍率とアニメーション中のコマも記録し、倍率経路が違うままのFPSを単純な速度向上率にしない。

各ワークロードは24段階in/outでウォームアップ後、24段階in/outを3往復。各方向の後に停止24rAFを別記録し、最後に16段階の共通倍率でドラッグ60コマを送る。前半より停止区間を長くしたのはLeafletの250msアニメーションを含めるため。全条件の停止区間は同じ。ドラッグは地図要素からmousedown/move/upを送り、DOMの通常のバブリングでDevのwindowハンドラ・Leafletのdocumentハンドラへ到達させる。全面版では慣性も有効で、同じ入力軌跡でも離した後の動きはDevと異なる。

各回は日英1F/5F×3条件×各4回=48試行、一試行に2ワークロードで計96測定。後述のA/Bの2回で計96試行・192ワークロード。各ケースの順序は`Dev,描画のみ,全面,全面,描画のみ,Dev,描画のみ,全面,Dev,Dev,全面,描画のみ`。各条件の平均順序をそろえた。ケースごとに候補2種を事前ウォームアップし、タイルの生成・取得状態は試行前後にも保存する。

rAF間隔はブラウザの描画処理による待ちの指標で、GPUが提示した実フレーム数ではない。特に標準CSSズーム中のJS倍率確定回数は、画面上の補間フレーム数ではない。物理トラックパッド・実機iPhoneのピンチを測ったものでもない。

### 途中の修正とデータの分離

- 比較用公開APIへ最初に配列を渡したところ地図座標と解釈されたため、画面座標を表す`L.point()`へ修正。正式な数値へ含めない。

### 判断・検証範囲

Aでは1Fの拡大縮小が描画のみ・全面移行とも約60FPSになったが、Bでは同じ描画実装でも両候補に低下が出た。**全面移行だけで安定して約60FPSになるとは、今回の結果から保証できない。** 全面移行が描画のみよりさらに速いとも結論づけない。Leafletへ操作をまとめる利点は標準ハンドラ・カメラを使えることで、Aの1F改善の共通点はPNGタイル描画への変更だった。5FはAのDevが約60FPSで、Bではタイル版に低下もあり、性能上の移行メリットを確認できていない。
