# 現在地表示・試作

## 試し方

プレビューの地図ページを開くと、最初の地図を描画した後で自動的に `getCurrentPosition` を呼ぶ。初回はブラウザの許可を求め、許可済みならそのまま `watchPosition` に移る。`?gps=1` や「その他」からの開始操作は不要。バックグラウンドで開いたページは表示されるまで待つ。編集画面や地図以外のページでは取得しない。

GPS用コードとCSSは最初の地図描画後に遅延読み込みし、最初の結果は読み込み中も保持する。自動開始で教室リンクや利用者の表示位置を動かさない。現在地ボタンはオン・オフに残し、明示的な再開ではタップ内から直接APIを呼ぶ。案内・エラー・再試行・停止をまとめたカードは削除した。状態と精度は現在地ボタンのtitle/アクセシブル名へ反映する。

- 概略の平面位置を表示中のフロア図に表示する。開始時に1Fへ切り替えず、選択中の階を維持する。自動開始ではパン・ズームを変えない。手動で再開した場合だけ、初回の有効な位置へ地図を移動する。
- 円は端末が報告する測位誤差をもとにした正円。座標補正と表示倍率を掛けた行列の最大特異値を半径の縮尺とし、元の楕円を覆うようにする。画面の縦横比も考慮してピクセル座標で描く。図面の補正誤差は含まれず、総合的な精度保証ではない。
- 1F〜5F、A棟・H棟6〜9Fに対応。6〜9Fの一覧図は各階の図へ同じ平面位置を表示する。利用者の階や室内位置は判定せず、階は手動で選ぶ。A/H棟の6〜9Fでは、GPS測位点がその棟の建物輪郭内にあり、端末の測位誤差円も輪郭内に収まるときだけ表示する。中庭・屋外・別棟にいる場合や、誤差が境界をまたぐ場合は点と円を隠す。位置・精度が改善したら自動で再表示し、測位監視は継続する。プリンター案内図は表示対象外。
- Google Mapsの現在地表現に合わせ、青い点（#1a73e8）に白い縁、淡い青（#4285f4、16%）の測位誤差円を使う。有効な現在地ボタンも青系で表示する。[Google Mapsヘルプ](https://support.google.com/maps/answer/2839911?hl=ja)
- 図にない範囲や100mを超える測位誤差は、点を置かず、現在地ボタンに状態を反映する。
- 現在地ボタンの再選択で監視を止める。再取得はオフ→オンで行う。非表示タブでは監視を休止するが、最後に取得した点は残す。時間経過、一時的な測位エラー、画面の非表示・復帰、bfcache復帰でも最後の点を保持する。新しい測位結果が棟外・不確実な場合の非表示判定は維持する。許可拒否後は自動で再要求を繰り返さない。
- 位置情報は画面表示用メモリー内だけで扱う。位置座標をサーバーへ送信・保存しない。

## 取得頻度と継続追跡

`watchPosition` を高精度指定（`enableHighAccuracy: true`）、キャッシュの許容時間0（`maximumAge: 0`）で継続する。届いた新しい測位結果は次の描画フレームで反映し、アプリ側で秒単位の間引きはしない。`timeout: 15000` は1回の取得の待ち時間であり、15秒間隔の更新指定ではない。

最初の位置を取得した後、画面が表示されている間に10秒間新しい測位が届かなければ、通常の監視を維持したまま `getCurrentPosition` でも再取得を試みる。こちらも高精度・キャッシュ許容0・タイムアウト15秒とする。

- 通常の更新が続けば補助の取得は行わない。端末が1秒ごとに結果を通知すれば、その都度反映する。
- 補助の要求は同時に1件まで。完了後、さらに10秒間更新がなければ再試行する。API要求の頻度と、実際に新しく測位できる頻度は異なる。
- 補助の応答が遅れても、新しい `watchPosition` の測位時刻より古い結果で点を巻き戻さない。新しい位置の後に届いた補助要求の一時エラーも表示を上書きしない。
- 非表示・明示停止・許可拒否で補助タイマーを止める。画面復帰時は監視を再開し、前の監視期間の応答は捨てる。キャンセルAPIのない補助要求は完了を待ち、復帰時も重複させない。
- 初回の許可待ちには補助要求を出さない。許可拒否後も自動で要求を繰り返さず、現在地ボタンをオフ→オンにする。最後の位置の表示は維持する。

Web Geolocation APIには測位間隔を秒数で指定する機能がない。更新頻度や移動とみなす基準は端末・ブラウザが決め、非表示の文書には更新が配送されない。したがって、Google Maps／Apple Mapsのネイティブアプリと同一頻度や、iPhoneをロックした状態での継続取得は保証できない。[W3C Geolocation仕様](https://www.w3.org/TR/geolocation/)

## 階ごとの図面補正

1Fの地理座標を基準に、図面内の同じ設備・外角を対応させる。2〜5Fは3点アフィン変換。A上層は3点変換にAN側の局所補正、H上層は4点の最小二乗アフィン変換を使う。日英は既存のSVG補正と整合させ、H棟上層はviewBoxの原点8.5を差し引いた座標を使う。

- 2F〜5F: H棟西側エレベーター、A棟西側エレベーター、B棟エレベーターを対応付ける。2F・3FのD棟は図の配置が別にずれるため、D棟北西角を個別補正する。
- A棟6〜9F: AS外角と2か所のエレベーターの3点変換を維持し、AN側の上端外角とコンコース階段で局所補正する。x=854.94より右だけ、y=359.891を境として上端／下端の測定残差をそれぞれ線形に混合する。全体の5点最小二乗はAS側の検証点を悪化させたため不採用。局所補正の微分も誤差円に適用する（範囲をまたぐ円は局所線形近似）。
- H棟6〜9F: 西端/東端エレベーター・南側階段に西端外角を加えた4点で、各図を最小二乗補正する。
- A/H棟の所属判定はsrc/assets/gps-building-footprints.jsonのOSM建物輪郭で行う。矩形の判定は使わず、中庭やH棟東側のくぼみも除外する。測位誤差円が外壁をまたぐ場合も隠す。GPSのreported accuracyは絶対的な位置保証ではなく、実際の在館や階の断定には使わない。
- 対応点は既存SVGの輪郭とsrc/assets/facility-ring-offsets.jsonの日本語座標から取得。1F基準の誤差に図面間の差も加わるため、現地での位置精度を保証するものではない。

## iPhoneの位置情報許可

最初の地図描画後に自動で許可を要求し、GPSコードのダウンロードを待たせない。許可画面で一時的にページが非表示になっても、保留中の要求を取り消さない。ユーザー操作を要求するブラウザでは、現在地ボタンをオフ→オンにするとタップから直接 `watchPosition` を呼ぶ。

サイトまたはOS側で拒否済みの場合、Webページからその判断を上書きしたり、必ずダイアログを再表示させたりすることはできない。変更箇所はSafariのページメニュー → Webサイトの設定 → 位置情報で「確認／許可」、端末の「位置情報サービス」の確認とする。アプリ内ブラウザではSafariで開く。[AppleのSafari設定案内](https://support.apple.com/ja-jp/guide/iphone/iphb01fc3c85/ios)、[Geolocation仕様](https://www.w3.org/TR/geolocation/)。

2026-10-23、実iPhone Safariで新しいプレビューを開き、現在地ボタンを押さずに位置情報の許可ダイアログが出ることを確認した。「許可」後は自動で青い点と誤差円が表示された。OS全体の権限設定は変更していない。自動試験では初回描画後の要求、ダウンロード待ち、許可画面相当のvisibility変化、拒否後の再試行、位置の保持を検証する。

## 実iPhoneでの確認（カード撤去前・2026-10-23）

iPhoneミラーリングを通じ、実機Safariで最新previewを確認した。最初は位置取得が即時拒否され、iPhoneの位置情報サービス自体はオンだが「SafariのWebサイト」が「しない」になっていた。設定変更の確認待ち中にユーザー側の画面操作が入り、その後は位置を取得できる状態になった。エージェントはOS権限を変更しておらず、許可ダイアログの操作は観測していない。

- 校内の屋内静止条件で、最終取得時刻の更新を複数回確認。画面上では少なくとも `:44 → :54 → 翌分:24 → :47 → 翌分:07` の測位時刻を観測した。連続的な画面録画ではないため、この差を全更新の周期とみなさない。
- 操作を加えずに端末の報告精度が約12mから11m、9m、8m、7mへ変化し、青い点はほぼ同じ位置を維持した。取得後10秒以上経過した結果が表示される場面もあり、毎秒更新は確認できていない。
- ユーザーが申告した教室を検索すると、青い点はその教室輪郭の下端付近に重なった。室内の正確な立ち位置や測量値はないため、実際の誤差距離は算定しない。報告精度7〜12mの円は複数の教室にまたがる。
- 別棟にいる状態でA棟6〜9Fへ切り替えると、「この棟の範囲外」として点が隠れることも確認。
- 途中のミラーリング切断・再接続タイムアウトを経て、接続復帰後も測位時刻が進むことを確認した。これは画面ロック中や非表示時の継続測位を確認したものではない。

この確認は屋内での1地点・静止条件。歩行時の追従速度、屋外の精度、複数端末、実際の測位誤差、継続取得時の消費電力は未検証。watchPositionと補助取得のどちらから来た更新かは画面だけでは区別できない。

## 測位点間の滑らかな移動（2026-10-24）

新しい測位結果を受け取ると、直前の表示位置から新しい位置へ200〜1000msで補間する。時間は実際の受信間隔に合わせ、途中で次の結果が届いた場合も現在の補間位置からつなぐ。緯度・経度を補間してから階・言語ごとの図面へ投影するため、階切り替えや拡大縮小でも共通の座標補正を維持する。青い点と誤差円は同じ位置を使い、円の大きさは最新の報告精度を維持する。初回表示は待たせず、受信した地点より先へ位置を予測しない。

SVGと円要素は移動中も再利用し、requestAnimationFrameで描画する。移動が終わると連続描画を止め、非表示時もアニメーションを止める。測位APIの受信間隔そのものは変更していない。


## 2026-10-24: 共通座標・推定・補間の更新

この節は旧階別変換・200〜1000ms補間に関する記述を置き換える。

- 1F〜5Fの表示は各言語の1F座標を共通フレームとする。GPSは緯度経度→局所メートル→共通フレームへ直接変換する。旧GPS用の階別アフィン変換とD棟の特例、およびGPSへの `alignFloorLocation` 再適用は廃止。地図・施設リング・検索領域は引き続き元の階の座標から既存の共通フレームへ登録する。
- 同じ緯度経度は同じ言語の1F〜5Fで同一の座標・誤差変換行列になる。A/Hの6〜9F合成図は別の紙面配置なので、既存の4パネル変換と棟内判定を維持する。GPSから階を推定しない。
- `geolocation-estimator.js` は地図と独立した局所メートル座標で精度・測位時刻差に基づく重み付けを行う。同一／過去時刻は再融合しない。歩行用プロセス雑音1.8m/s、測定重みは `max(3, accuracy/2.448)^2`。これはチューニング上のガウス相当尺度であり、端末の誤差分布を証明したものではない。
- 直前の精度＋新しい精度＋3m/s×時間差＋5mを超えるジャンプは保留。5秒以内の互いに整合する3回の測位で復帰し、15秒以上の空白は最新測位にリセットする。高速移動を永久に排除しない。100mを超える不確かな測位は推定に融合しない。
- 補間は受信間隔の25%、100〜250ms。途中更新では描画中の位置から再開し、最後の推定点の先まで外挿しない。推定処理による遅れと描画補間の遅れは別である。
- 誤差円は推定・補間後の点を中心にし、最新の生測位点からの画面距離＋生測位の投影誤差半径以上とする。フィルタで精度が良くなったように半径を縮めない。円は端末由来の不確かさを示すもので、案内図自体の校正誤差や誤った測位の全てを保証しない。

### 地理校正の評価と残る制約

`src/assets/gps-calibration.json` に既存の3校正点・4独立照合点・変換係数を分離して保持する。`node scripts/gps/evaluate-calibration.mjs [candidate.json]` は校正点だけで候補係数を推定し、独立照合点のRMSEと最大誤差、対応点の分布、探索用leave-one-outを出す。実行しても本番係数を書き換えない。

既存データでは独立照合点に最大約7.16mの図面対応残差があり、7点のleave-one-out最大は約8.17m（各候補変換の逆行列によるメートル換算）。校正点のSVG y範囲は104〜332、B棟南東側y≈802を含まない。追加の独立した地理対応点を特定せずに係数を変えても精度向上を証明できないため、今回の本番係数は保持した。新規機器は不要だが、同じ角・入口だと確実に識別できる地理座標と図面点が必要。合成緯度経度による階間一致テストは地理的な実測精度の証拠にしない。

### 通路・壁の補正（今回未適用）

描画しない歩行領域を用意する考え方でよい。ただし領域だけでは接続が分からない。階・棟を持つ通行可能ポリゴン、ドア／入口／階段／EVのノード、通行可能な接続辺、壁・閉鎖区間が必要。検索用部屋領域だけから自動生成して室内の人を廊下へ吸着させない。GPS・時刻・精度から複数候補を評価し、競合時は曖昧さを残す。階変更は利用者の選択などを用い、水平GPSだけで決めない。接続データをまだ用意していないため、今回は壁越え判定・通路吸着を追加していない。QR・BLE等の追加設置は対象外。
