# Ver3.2 機能検討

ブランチ: `Version3.2`

説明: 位置情報表示機能の追加

## 検討の前提

- 作成日: 2026-10-23。
- 作業ブランチ: `Version3.2`（旧名 `codex/ver3.2`）。取得時の最新 `origin/main`（`03ab05895082ce0c81c44d6db9f18bf8d3288f28`）から作成。
- 素材: ユーザーが提示した、SVG地図制作者とのチャット。
- 以下はチャットから抽出した考え方と、現在のOICマップに当てはめた提案。Ver3.2への採用・仕様・実装順は未決定。

## 1. 詳細度は「利用者が次に判断すること」から決める

チャットでは、詳細地図にすると便利になる一方で、細部への要求が際限なく増えること、一本道なら地図の必要性自体が低いことが指摘されている。

OICでは「施設の位置が分かる」から先の、到着までに迷う箇所を優先する。候補は建物の出入口、棟間の接続、階を移動する階段・エレベーター、目的の部屋に入る側。階段などの施設表示は既存なので、追加の価値は接続先や入口との関係にある。

最初から全通路の自動経路案内へ広げず、特定の出入口から特定の教室へ行く場面を選び、実際に迷う地点を確かめる。案内の完成度は、図形の数より「次にどこへ進むか分かるか」で判断する。

## 2. 独自地図では、移動を左右する構造を充実させる

階段・壁・柵まで描くという話から拾えるのは、装飾を増やすことより、通れる場所と通れない場所を分かるようにする発想。

OICでは、通り抜けできない境界、渡り廊下、出入口、段差の有無などが候補になる。利用制限や段差を載せる場合は、確認できた範囲をデータにする。単に地図上で近いことから、通行可能・利用可能と推定しない。

将来、自動経路案内へ進む場合には、地図の絵とは別に、通路と階移動の接続データが必要になる。現在の検索座標・部屋外周だけで経路を生成する設計にはしない。

## 3. 情報を持つことと、常時表示することを分ける

「利用者が求める詳細度との乖離」という指摘は、情報量の出し方を見直す材料になる。

現在の地図には施設別リング、検索で選んだ部屋の外周、食事カードがあり、必要時に強調する構成がすでにある。新しい設備情報もこの構成を使い、選択した施設の詳細に出す。縮小時は棟・出入口、拡大時は部屋・設備という表示も将来候補になる。

ただし、元SVGには文字・記号が描き込まれている。縮尺別に消すにはSVGのレイヤー整理等が必要で、表示条件を付けるだけで実現するとは限らない。情報の整理が、そのまま描画速度の改善になるとも限らない。

## 4. オフライン利用は「必要な地図を保存しきる」単位で考える

チャットの「GPS付きオフラインマップ」から、通信が途切れても地図を使える価値を取り出せる。現在位置とオフライン保存は、別々に設計・検証できる。

現行にはPWAとService Workerがある。`public/sw.js` は一部HTML等を事前保存し、取得した静的資産をキャッシュするが、全階のSVG・検索データ・施設データを一括で事前保存する構成ではない。「一度サイトを開けば、未表示の階も使える」とは扱えない。

候補は、利用言語を選んで地図と検索情報をまとめて保存する機能。保存対象、容量、完了・失敗、更新日を分かるようにする。営業状態などの動的情報には別の鮮度管理が必要。

検証では、保存後に通信を切り、初めて開く階・教室検索・施設表示・再起動を確認する。ホーム画面へ追加できることだけでは、オフライン利用の検証完了にしない。Service Workerによる事前保存の基本は[MDNの解説](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers)を参照。

## 5. 設備情報は、固定情報とリアルタイム情報を分ける

「トイレの個室数が分かると便利」という話は、場所に設備の属性を足す発想として取り入れられる。

個室の総数、多機能トイレの設備、プリンターの対応サービスなどは、現地や資料で確認して登録する固定情報。個室数を掲載するだけならセンサーは不要。一方、「今いくつ空いているか」は観測と継続運用が必要な別機能になる。

Ver3.2の候補としては、まず既存の施設表示から詳細を開き、確認済みの設備情報を読める形が考えられる。登録する項目を絞り、出典・確認日・不明を管理する。空欄をゼロや「設備なし」に読み替えない。

## 6. 現在位置を出すなら、誤差を含めて伝える

「ずれる」という不満は、地図の位置合わせ、端末の測位誤差、利用者が期待する精度を分けて検討する材料になる。チャットにある「自然が豊かなので精度が課題」という推測だけから、測位条件や改善策を確定しない。

現行の閲覧コードではGeolocation APIの利用は見当たらない。導入には緯度経度とSVG座標を対応付け、基準点と現地で位置合わせを検証する工程が必要。地図画像のトレースだけで地理座標の正しさは得られない。

ブラウザーの位置取得には利用者の許可が必要で、APIはメートル単位の精度情報も返す（[Geolocation API](https://developer.mozilla.org/en-US/docs/Web/API/Geolocation_API)、[accuracy](https://developer.mozilla.org/en-US/docs/Web/API/GeolocationCoordinates/accuracy)）。提案としては、屋外の概略位置から試し、誤差範囲を表示する。屋内の部屋・階を確定する根拠にはしない。

位置が取れない場合にも使えるよう、建物の入口などを出発点として手動で選ぶ案を比較する。

## 7. 見た目は、識別しやすさを基準に改善する

背景のグレーや草地の形への意見は、チャット相手の地図に対するもの。現在のOICマップが同じ問題を持つ証拠ではない。

OICへ取り入れるなら、棟、屋外、通路、選択中の施設が区別できるかを、初見利用者とスマートフォンの画面で確認する。既存の白・淡いグレー・えんじを基調とするUIを出発点にする。緑地を曲線化するなどの描き直しは、道や入口を見つけやすくなる根拠がある箇所に絞る。

## 8. 制作の自動化と、正しさの確認を分ける

「屋外はOSM」「フロア図の整理はAI、デザインは人」という話から、用途ごとに素材・工程を分ける考え方を取り入れられる。

現在はフロアSVGと検索・施設データを分けて管理している。抽出、座標変換、登録候補の列挙、日英の差分検出を自動化し、人が施設の意味・入口・接続・読みやすさを確認する分担が合う。

OSMの導入は、周辺道路からキャンパス入口までの案内を必要とする場合の別候補。今回の会話だけでは、既存のフロアSVGや操作系を置き換える理由にはならない。

## Ver3.2に向けた優先候補

| 優先度案 | 候補 | 最初に確かめること |
| --- | --- | --- |
| 高 | 出入口・棟間接続・階移動の案内 | 代表的な移動で迷う箇所と、現行データの不足 |
| 高 | 地図・検索のオフライン保存 | 現行キャッシュの不足、保存容量、保存後の未表示階と検索 |
| 中 | 施設の設備詳細 | 必要な項目、確認できる情報源、更新負担 |
| 中 | 表示する情報の整理 | 初見利用者に不要な表示、元SVGの編集範囲 |
| 別途実験 | 屋外の現在位置 | 座標対応、実測誤差、利用許可がない場合の操作 |
| 後続検討 | 自動経路案内・リアルタイム空室 | 接続・観測データの整備と継続運用 |

まず代表的な利用場面を決め、使いやすさとデータ更新量を確かめて採用範囲を決める。すべてをVer3.2へ詰め込む前提にはしない。

## 描画性能の最適化との関係

このチャットには、SVGのパス削減、mask/filterの簡略化、タイル化などの具体的な高速化手法は含まれていない。今回抽出した内容は主に、案内・情報表示・通信への耐性・制作工程の改善。

描画の改善は既存の[地図性能の検証まとめ](map-performance/SUMMARY.md)を別の根拠として検討する。過去の検証は当時のDevを基準にしたものであり、現行mainの効果やVer3.2への採用を確定したものではない。
